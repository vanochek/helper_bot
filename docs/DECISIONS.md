# Решения

- Python 3.14: уже установлен, совместимость подтверждается uv.lock и тестами.
- Версии из архитектурного предложения не являются установленными: источник фактических Python-зависимостей — uv.lock.
- PostgreSQL 18 в Docker; порт только localhost:55432.
- Модели AI пока не закреплены: доступность в API проверить при реализации адаптера.
- CI/CD не добавляется согласно архитектурному ограничению.
- Учётные данные локально генерируются bootstrap; API-ключ предоставляет владелец перед интеграцией AI.

## Этапы 1 и 2

- Владелец — анонимная браузерная сессия, без аккаунтов; хранится SHA-256 токена.
- Одна таблица entries согласно архитектурному предложению; UUID генерирует сервер.
- Ограничения времени и типов действуют и во входной модели, и в PostgreSQL.
- Зона проверяется по IANA при создании сессии; точные времена без зоны отклоняются.
- Полные составные индексы владельца/времени, владельца/даты и владельца/создания
  пока предпочтены частичным: проще схема, включают записи без срока.
- Поисковый GIN-индекс откладывается до реализации поискового запроса на этапе 3.
- Транзакции принадлежат прикладному сервису, репозиторий не делает скрытый commit.
- Cookie, Origin и определение владельца из HTTP реализуются до публикации предметного API.

## Этап 3

Cookie и Origin подключены. Поиск — PostgreSQL russian plainto_tsquery, вычисляемый
TSVECTOR и GIN; сырое выражение индекса заменено отдельной миграцией для корректного
сравнения схемы Alembic. API не принимает владельца. Даты периода — локальные даты
сессии, исключительная верхняя граница. Источник разрешённых запросов задаётся APP_ORIGIN.

## Этап 4

Время разрешается из типизированного кандидата. Часы читаются сервером один раз.
Совпадение названного дня недели с сегодняшним требует уточнения, иначе выбирается
ближайший будущий день. Конец недели — воскресенье как дата. Неделя начинается
в понедельник. Прошлое не переносится автоматически. DST-провалы и повторы требуют
уточнения; календарные выборки используют то же ядро проверки границ.

## Этапы 5–7

LLM возвращает структурированное намерение через Responses API; разрешённые операции
выполняет сервер. Один draft на сессию, срок 30 минут, до 6 сообщений. Для идемпотентности
используется составной ключ session_id/request_id и блокировка сессии. Это сознательная
сериализация небольшого прототипа, не очередь обработки. Ключ и модель задаёт владелец.

## Этап 8

STT отдельным запросом, затем проверка текста пользователем и обычный chat.
Сырое тело с потоковым пределом 10 МиБ, запись браузера до 60 секунд.
TTS — speechSynthesis, выключен по умолчанию; аудио постоянно не хранится.

## Этап 9

Ограничения в памяти одного процесса — временная граница локального прототипа;
публичное развёртывание требует общего лимита proxy и бюджета провайдера.
Копии восстанавливаются только в новые БД; рабочая база не перезаписывается.
Политика автоматического удаления данных не назначается без решения владельца.

## Этап 10

Сервер и домен ещё не выбраны пользователем. Подготовлен отдельный Compose-профиль
с HTTPS Caddy и ограничениями Nginx. Приложение не владеет схемой БД.
