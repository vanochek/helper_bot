# Эксплуатация и приёмка

## Поддерживаемый режим

Сейчас поддерживается один процесс приложения и локальная Compose-БД. Лимиты
хранятся в памяти процесса и сбрасываются при перезапуске. Это не распределённая
защита и не денежный бюджет. Перед публичной публикацией обязательны HTTPS,
общий лимит на reverse proxy, бюджет/квота API-проекта и отдельная роль БД с
минимальными правами. Compose-пользователь helper — локальный администратор,
его нельзя использовать как production-роль приложения. Это задачи этапа 10.

## Ограничения запросов

На процесс: 600 API-запросов/минуту, на адрес клиента — 120. Для POST chat/messages
и speech/transcriptions дополнительно 40/минуту суммарно и 10/минуту на адрес.
Окна фиксированные; на их границе возможен всплеск. Ключи ограничены 4096 элементами.
Отклонение: 429 и Retry-After: 60. Неудачные попытки тоже учитываются.
IP определяется ASGI-сервером: за proxy необходимо явно настроить доверенные адреса,
не доверять произвольным X-Forwarded-For. При нескольких клиентах за NAT лимит общий.
Повторы чата сохраняют прежний request_id и ждут освобождения лимита.

JSON API ограничен 16 КиБ до разбора тела; аудио — 10 МиБ. Проверяется фактическое
количество байтов, включая chunked-запросы. Медленные соединения, число одновременных
загрузок и лимиты соединений должен ограничивать сервер/reverse proxy при публикации.
CSP запрещает сторонние скрипты на странице приложения; Swagger/ReDoc оставлены
с отдельным исключением для штатных ресурсов. Есть nosniff, запрет iframe,
no-referrer, запрет камеры и доступ к микрофону только самому сайту.

## Диагностика

python dev.py check — полная проверка, включая отдельные схемы PostgreSQL и Docker
для теста резервного копирования. python dev.py smoke — миграции и готовность API.
/health/live проверяет процесс; /health/ready — подключение и наличие рабочих таблиц/полей.
Проверка актуальности миграций: python -m uv run alembic check.

Каждый ответ получает X-Request-ID, созданный сервером. JSON-лог содержит только
request_id, HTTP-метод, шаблон маршрута, статус и длительность. Тела, query string,
IP и cookie в него не попадают. dev.py serve отключает стандартный access log Uvicorn,
чтобы тот не печатал поисковые запросы. При собственном запуске также указывайте
--no-access-log. Не включайте отладочные логи SDK с персональными данными.

## Резервные копии

Без флагов команды используют локальный Compose-сервис db и базу helper.
Для production-профиля добавьте --production (см. DEPLOYMENT.md):

- python dev.py backup — согласованный pg_dump -Fc в backups/ с уникальным именем.
- python dev.py restore-check [путь] — восстановить копию в новую случайную БД,
  прочитать ревизию и количества записей, затем удалить только эту временную БД.
  Без пути сначала создаётся свежая копия.
- python dev.py restore-new [путь] — восстановить в новую БД restore_<uuid> и оставить
  её для ручной проверки/переключения DATABASE_URL. Существующая БД не перезаписывается.

Копии содержат персональные данные, историю и хеши токенов. backups/ исключён из Git,
но не зашифрован: храните копии на защищённом носителе с ограниченными правами.
Автоматическое расписание не создавалось. Предлагаемый режим: ежедневно и перед
миграцией, минимум 7 ежедневных копий; удаление старых копий — отдельная операция.
Не загружайте недоверенные дампы: восстановление исполняет SQL из архива.
Если restore-new завершился ошибкой, новая БД может остаться для диагностики,
её имя видно в сообщении ошибки команды; рабочая helper не изменяется.

Проверенный сценарий аварии: остановить приложение, выбрать доверенный дамп,
restore-new, сверить данные и ревизию, при необходимости применить миграции к новой БД,
поменять DATABASE_URL, запустить приложение и выполнить smoke. Старую базу сохранить
до подтверждения восстановления. Откат кода после миграции требует анализа совместимости;
не запускать downgrade автоматически на рабочих данных.

## Матрица приёмки

| Область | Доказательство |
|---|---|
| Создание задачи, встречи, напоминания | test_api, test_storage, test_chat |
| Список за период, поиск словоформ | test_api, test_chat |
| Даты, уточнения, DST | test_temporal, test_chat |
| Чужие записи/история, Origin | test_api, test_chat, test_speech |
| Повтор, конкуренция, отказ commit | test_chat |
| Голос → текст → действие | test_speech с тестовыми STT/AI |
| Лимиты, заголовки, приватность логов | test_guardrails |
| Backup/restore с контрольной записью | test_backup, отдельные временные БД |
| Настоящие формулировки и распознавание | Ожидает API-ключа и доступных моделей |
| Микрофон/голос пользователя, HTTPS | Ожидает устройства и развёртывания |

Тестовые AI/STT не подтверждают качество реальной модели. Для живой приёмки после
настройки пройти все примеры docs/MVP.md, повторить голосом, проверить отмену,
уточнение, перезагрузку и отсутствие дубля. Не считать этап полностью принятым,
пока этот прогон не выполнен и не записан его результат.

## Хранение и удаление данных

История и ключи идемпотентности пока хранятся без автоматического удаления. Удаление
истории отдельно от записей может разрешить старый повтор запроса; поэтому очистка
должна удалять целую сессию каскадно после выбранного владельцем срока. Автоматическая
очистка не включена, чтобы не уничтожать данные без принятой политики хранения.
